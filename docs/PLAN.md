# PlayScout（工作名）产品方案

> 本文保留产品方向与商业目标。进入开发时，以 [IMPLEMENTATION_SPEC.md](./IMPLEMENTATION_SPEC.md) 为功能与数据标准，以 [UI_DESIGN_SYSTEM.md](./UI_DESIGN_SYSTEM.md) 为界面规范，以 [ROUTE_CONTENT_MATRIX.md](./ROUTE_CONTENT_MATRIX.md) 为内容量与跳转标准，以 [BUILD_BACKLOG.md](./BUILD_BACKLOG.md) 为开发顺序。

## 1. 产品定位

面向英语用户的移动游戏发现与攻略平台。榜单负责让用户发现游戏，攻略、兑换码、活动日历、视频和玩家经验负责解决问题并促成回访。

核心价值：在一个页面里回答“什么游戏正在火”“值不值得玩”“怎么开始”“现在要做什么”“别人是怎么做的”。

Pocket Gamer 可借鉴的部分是按平台和内容意图组织入口、突出热门游戏专区、持续产出攻略／兑换码／榜单；PlayScout 的差异点是实时榜单、结构化游戏资料、版本与证据标记、工具和玩家贡献闭环。

## 2. 用户与主要任务

1. 新玩家：找近期热门或刚上线的手游，快速判断是否值得下载。
2. 活跃玩家：查询角色强度、活动规则、资源分配、关卡打法和兑换码。
3. 回流玩家：了解版本变化和回归后的优先事项。
4. 内容作者：提交攻略、视频和纠错，并获得署名及个人主页曝光。

## 3. 内容分层

### A. 全量游戏资料库（覆盖面）

- 目标首年 3,000–10,000 个游戏实体页。
- 字段：名称、平台、发行商、国家、分类、标签、上线日期、商店链接、价格、内购、评分、年龄等级、语言、截图、视频、版本历史和榜单快照。
- 资料页以结构化事实为主，不自动生成空泛攻略。

### B. 重点运营游戏（稳定更新）

- 同时维护约 30 款游戏。
- 每款 8–20 个可解决具体问题的页面：新手、活动、角色／装备、FAQ、版本变化、兑换码和视频精选。
- 选择依据：榜单持续性、搜索需求、更新频率、内容缺口和商业价值。

### C. 旗舰游戏中心（内容深度）

- 同时深耕 8–12 款，如 Whiteout Survival、MONOPOLY GO!、Pokémon GO、Roblox 子游戏、Minecraft、Kingshot 等。
- 每款 30–80 个页面，配套至少一个实用工具，例如升级计算器、阵容构建器、事件倒计时或收藏清单。
- 建立玩家作者与固定校验人。

## 4. 网站信息架构

- 首页：趋势条、主编辑推荐、实时榜单、热门游戏中心、最新上线、最新攻略、视频精选、兑换码和玩家分享。
- 榜单：iOS／Android／Steam；国家、设备、免费／付费／畅销、新上榜、涨幅和分类筛选；保存每日快照。
- 最新游戏：本周上线、即将上线、抢先体验、软启动和地区可用性。
- 游戏中心：概览、入门路线、攻略树、角色／装备资料、活动日历、兑换码、视频和玩家经验。
- 内容频道：新闻、攻略、Tier List、兑换码、评测、最佳游戏、视频和工具。
- 社区：投稿、纠错、方案分享、视频推荐、作者档案和贡献信誉。

## 5. 数据与内容获取

### 优先级 1：官方和授权来源

- App Store：公开榜单／Search API、商店元数据和发行商提供的媒体素材。
- Google Play：公开商店信息；榜单数据优先采购合规数据服务，自动采集前核对服务条款和 robots 规则。
- Steam：Steamworks Web API、商店公开信息、官方新闻。
- YouTube：Data API 搜索，限制为可嵌入视频，保存视频 ID、频道、时长、发布日期和最后检查时间；页面使用官方播放器嵌入。
- Twitch、Reddit 等：使用官方 API 或明确许可方式，仅保存必要元数据与原始链接。
- 游戏官方站、新闻稿、Fan Kit、Discord 公告：提炼事实，保留来源和时间，不复制完整文章。

### 优先级 2：编辑与玩家生产

- 编辑实测：截图、录屏、步骤、版本和结果。
- 合作作者：按明确任务约稿，每份素材包含原始截图／视频和发布授权。
- 玩家投稿：保留作者署名、原始链接、授权范围及纠错记录。
- AI：完成聚类、摘要、翻译、格式化和旧内容预警；涉及数值、兑换码、活动时间和打法的内容必须人工确认。

### 必须保存的追溯字段

`source_url`、`source_type`、`publisher`、`retrieved_at`、`usage_basis`、`game_version`、`region`、`verified_by`、`last_verified_at`、`content_hash`。

## 6. 榜单与热度算法

展示三类榜单，避免把不同含义混成一个排名：

1. 商店榜：各平台和国家的原始名次与历史变化。
2. 社区热度榜：YouTube 近期视频观看增长、Reddit 讨论量、Twitch 观看量等归一化信号。
3. PlayScout 热门榜：站内搜索、内容阅读、关注、收藏和外部热度的组合分。

示例：`热度 = 35% 商店排名 + 25% 搜索趋势 + 20% 视频增长 + 10% 社区讨论 + 10% 站内行为`。页面公开权重、更新时间和数据来源。反作弊时降低单一异常信号权重。

## 7. 100k 月 PV 增长模型

100k PV 是结果目标，不能承诺。规划基线为 72,000 月访问 × 1.4 页／访问 ≈ 100,800 PV。

### 0–2 月：建库与验证

- 12 个旗舰游戏中心、150 个高意图页面、300 个基础游戏页。
- 重点做“兑换码、活动、角色排名、新手问题、具体关卡”和新游戏首发内容。
- 目标：建立索引、获得首批长尾排名和玩家反馈。

### 3–4 月：形成主题权威

- 累计 350–500 个高质量内容页、1,500 个资料页、6–10 个轻工具。
- 每周：20–30 次旧内容复核、12–18 篇新内容、2–3 个视频合作、1 个榜单专题。
- 建立相关页面内链：榜单 → 游戏中心 → 新手路线 → 具体攻略 → 工具／视频。

### 5–8 月：冲击 100k PV

- 累计 700–1,000 个可搜索内容页，重点页面维持版本新鲜度。
- 假设头部 50 页平均 600 PV／月，腰部 250 页平均 180 PV／月，长尾 500 页平均 50 PV／月，可形成约 100k PV。实际结果取决于竞争强度、域名积累和内容质量。
- 用 Search Console 数据每两周调整游戏覆盖，停止产出没有展示或玩家价值的模板页。

## 8. SEO 与留存设计

- 每个搜索意图一个明确页面，答案置顶，并标注版本和更新时间。
- 使用 Game、VideoObject、Article、BreadcrumbList 等适用的结构化数据；不标注页面没有的内容。
- 游戏中心使用主题集群和面包屑，避免标签页批量生成重复薄页。
- 兑换码和活动页显示“最后验证”，过期内容自动归档并保留历史记录。
- 通过关注游戏、活动提醒、每周邮件和浏览历史提高回访；需要登录的功能延后到第二阶段。

## 9. 技术架构建议

- 前端：Next.js 或同类支持静态生成与增量更新的框架，榜单和资料页优先服务端渲染。
- 内容：Headless CMS 管理文章、作者、版本和审核流程。
- 数据：PostgreSQL 保存游戏实体、榜单快照、来源、文章、视频和玩家贡献；对象存储保存自有／授权素材。
- 采集：任务队列分来源运行，原始层、规范化层和发布层分离；差异检测后只重审发生变化的字段。
- 搜索：首期用数据库全文检索，数据量与需求上升后再使用独立搜索服务。
- 监控：来源失败、排名异常、失效视频、过期活动、内容未复核和流量下降都进入编辑队列。

## 10. 第一阶段交付范围（6–8 周）

1. 首页、榜单、最新游戏、游戏中心、文章、视频、兑换码、搜索和投稿入口。
2. 12 个旗舰游戏、300 个基础资料页、150 个经过编辑的攻略／榜单／活动页。
3. App Store 榜单管道、YouTube 可嵌入视频管道、一个 Android 数据来源和来源追踪后台。
4. 一个资源计算器、一个活动日历、内容版本与纠错流程。
5. SEO 基础、分析事件、站点地图、缓存和性能监控。

## 11. 原型说明

`index.html` 展示首页桌面／移动响应式原型；`game.html` 展示游戏中心原型。榜单标签、站内搜索和兑换码复制为可交互示例。当前图标和截图来自公开 App Store 展示素材，仅用于内部原型；正式上线前必须逐游戏确认素材政策和使用范围。
